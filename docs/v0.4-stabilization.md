# Sunbird v0.4 Stabilization Pass

This pass hardens the shared `v0.4-next` runtime before the JRPG and `v0.4-solo` lines diverge.

## Turn ordering

`TurnPlanner` now buffers the controlled entity's command before NPC behavior commands. Runtime `EntityId` allocation order no longer decides gameplay priority.

The current JRPG policy is therefore explicitly **controlled actor first, then NPCs in World entity order**.

`Simulation::Commands::Buffer` remains the batch boundary and preserves command order.

## World entity lifecycle

Two local-runtime outcomes are now distinct:

- `Defeat` retires an entity by removing gameplay/presentation components while retaining its `EntityId`, position, and zero Health as tombstone-like state.
- `Despawn` removes an active local entity from the World, clears its components and runtime relations, and does not reuse its `EntityId`.

`Commands::Despawn` is intentionally limited to unbound local entities. A World entity bound to a persistent Session Character cannot be removed through the local despawn command; character transitions need an explicit higher-level lifecycle operation later.

## Invariants

The pass also establishes:

- duplicate Prototype names are rejected;
- spawning the same persistent Character twice fails before creating an orphan World entity;
- World relation edges are removed when either endpoint is despawned;
- active World entity enumeration excludes despawned entities.

## Shared cardinal directions

Cardinal deltas now live in `Sunbird::Direction` and are reused by movement-facing resolution, interaction, wandering, and pathfinding.

This removes multiple independent copies of north/east/south/west vectors.

## Hardcoded-value audit

Removed/centralized runtime duplication:

- Kitty unsupported-terminal text now interpolates `Sunbird::VERSION` rather than embedding `v0.3d` separately.
- cardinal direction vectors are centralized in `Direction`.
- turn priority is explicit policy rather than an accidental consequence of EntityId allocation.

Values intentionally still local to their domain:

- hero/mage starting HP, MP, attack and party composition in `App` are demo/bootstrap game data;
- Prototype glyphs, render layers, enemy attack values and Level coordinates are authored content;
- Kitty image/placement IDs, chunk size, tile geometry and terminal escape sequences are renderer/protocol constants;
- terminal Escape timeouts and byte limits are named adapter constants (and the active input timeout is injectable);
- behavior names such as `:chase` and relation kind `:targets` are current gameplay vocabulary.

The remaining App bootstrap data is the main candidate to move into authored game/session content later. It is intentionally not abstracted in this stabilization pass because the JRPG and `v0.4-solo` branches may want different bootstrap formats.
