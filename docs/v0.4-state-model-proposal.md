> **Historical proposal:** this document records the earlier design exploration that introduced `AreaState` and `ActorState`. The implemented `v0.4-next` cleanup later simplified those ideas into `World`, `Character`, `Prototype`, `EntityId`, Simulation-owned bindings, and `Executor`. See `architecture.md` and `v0.4-foundation.md` for the current design.

# Sunbird v0.4 State Model Proposal

**Status:** design proposal only; not implemented in v0.3d.

## Purpose

v0.3d exposed a useful architectural boundary and also made its weaknesses visible.

The current model has:

```text
Session
  persistent party identity + HP/MP

Level
  immutable authored area

World
  mutable state for one loaded Level
```

This works, but several concepts are beginning to collide:

- `World` sounds like the whole game world or overworld, while it currently means one local mutable runtime container.
- Session now owns persistent vitals but will eventually need more persistent actor/game state.
- Party identity is stable, while local World instances use transient integer `InstanceId`s.
- Battle currently knows whether an effect belongs to World or Session.
- Player HP is persistent, but player attack is still stored in local World `Combatant`.

v0.4 should redesign these boundaries before more RPG systems are layered on top.

## Design goals

1. Preserve the distinction between **persistent game state** and **local instantiated state**.
2. Do not merge Session and World into one universal object.
3. Free the word **world** for actual game semantics such as overworld/world map.
4. Make stable actor identity and local runtime identity explicitly different concepts.
5. Give persistent party/actor state a natural place to grow.
6. Avoid duplicated authoritative copies of the same value.
7. Make gameplay effects route through an explicit authority boundary rather than allowing modes/scripts to mutate arbitrary stores.
8. Keep the design suitable for later Rust + Lua production-runtime experiments.
9. Keep renderer choice (Kitty/Raylib) independent from the state-model redesign.

## Proposed vocabulary

Preferred working vocabulary:

```text
Session
  persistent game state

Level
  immutable authored area definition

AreaState
  mutable instantiated state for one loaded Level

ActorState
  persistent state for an important/stable actor

InstanceId
  local runtime identity
```

`AreaState` is the preferred replacement candidate for the current `World`.

Alternative names worth reconsidering during implementation include `SimulationState`, `LocalState`, and `AreaRuntime`. `Runtime` alone should probably be avoided because the term is overloaded.

## Proposed lifetime model

```text
persistent
────────────────────────────────────────
Session
├── Party
├── ActorState registry
├── Inventory          (later)
├── progression/flags  (later)
└── location/transition state (later)

authored / immutable
────────────────────────────────────────
Level
├── Terrain
├── Spawns
├── static Relations
└── authored metadata

local / instantiated
────────────────────────────────────────
AreaState
├── local runtime instances
├── Position
├── Facing
├── Collision
├── Behavior
├── local enemy Health
├── runtime Relations
└── local environmental state
```

## Session

Session remains the persistent root.

It should not become an unstructured bag of unrelated hashes. Instead, it should own clearly named persistent domains.

Possible eventual structure:

```text
Session
├── Party
│   ├── leader
│   └── ordered member identities
│
├── Actors
│   ├── :hero  → ActorState
│   └── :mage  → ActorState
│
├── Inventory
├── Flags
└── current location / transition state
```

Only the pieces justified by actual gameplay should be implemented.

## Party

Party should remain a **roster/control structure**, not the owner of every character attribute.

Preferred responsibility:

```text
Party
├── members
├── order
└── leader
```

Persistent member data belongs in ActorState keyed by the same stable identities.

This keeps:

```text
Party = who is in the group
ActorState = what persists about each actor
```

## ActorState

v0.3d has only `Session::Vitals`.

v0.4 should consider replacing or embedding that into a broader persistent actor object.

Conceptually:

```text
ActorState(:hero)
├── Vitals
│   ├── hp
│   ├── max_hp
│   ├── mp
│   └── max_mp
│
├── Stats
│   ├── attack
│   └── ...
│
├── Equipment      (later)
└── Progression    (later)
```

Do not implement empty categories merely because they appear in the diagram.

The immediate justification is to move genuinely persistent combat attributes such as player attack out of local runtime representation.

## AreaState

`AreaState` would replace the current engine meaning of `World`.

Its responsibility is the mutable instantiated state of one loaded Level.

```text
Level
  ↓ instantiate
AreaState
```

It owns things that naturally disappear or reload with an area: runtime InstanceIds, positions, facing, collision, local enemy HP, local behavior, runtime relations, and local environmental state.

It does **not** own persistent party HP, MP, equipment, progression, or inventory.

## Stable identity versus runtime identity

This distinction should remain strict:

```text
stable persistent identity
:hero

local runtime identity
InstanceId(17)
```

Session/ActorState uses stable identity. AreaState uses InstanceId.

Never store a local `InstanceId` as the persistent identity of a party member.

## Explicit binding

v0.3d lets Exploration keep a small mapping from party member identity to current runtime instance.

v0.4 should consider making this concept explicit:

```text
ActorBinding
  stable_actor_key: :hero
  instance_id: 17
```

The exact type/name is undecided. The binding belongs to the lifetime of the loaded area/mode, not to persistent Session state.

## Persistent and local actors

Persistent party actor:

```text
Session::ActorState[:hero]
        |
        | runtime binding
        v
AreaState InstanceId(17)
├── Position
├── Facing
├── Collision
└── Renderable
```

Local disposable enemy:

```text
AreaState InstanceId(42)
├── Position
├── Health
├── Combatant
├── Behavior
└── Collision
```

A persistent NPC can later combine both models if gameplay actually requires it.

## Mutation authority

v0.3d currently has:

```text
Resolver
  mutates World/local state

Session methods
  mutate persistent vitals
```

This avoids duplicated HP but makes BattleMode responsible for routing effects to the correct authority.

v0.4 should explore an explicit gameplay-effect boundary:

```text
gameplay logic / mode / Lua
          |
          v
        Effects
       /       \
local effect   persistent effect
     |              |
     v              v
 AreaState       Session
 authority       authority
```

Example effect vocabulary might eventually include:

```text
DamageLocal(instance_id, amount)
DamageActor(:hero, amount)
HealActor(:hero, amount)
SpendMp(:mage, amount)
DefeatLocal(instance_id)
```

These names are illustrative, not an API commitment.

## Commands versus effects

The existing `Simulation::Commands` work well for local World mutation.

v0.4 should decide whether to:

1. broaden Commands into a cross-domain effect system;
2. keep local Commands and add a sibling persistent Effect layer; or
3. introduce a higher-level turn/action resolver that emits both.

Do not choose solely for abstraction symmetry. Prefer the smallest model that keeps mutation authority explicit and is easy to port to Rust.

## Battle implications

A cleaner future battle path could be:

```text
BattleMode
    |
    v
BattleAction / intent
    |
    v
BattleResolver
    |
    +--> persistent Actor effects
    |
    `--> local Area effects
```

BattleMode would stop directly calling both `Simulation#step` and `Session#damage`.

This is especially attractive if later Lua scripts produce battle intent: Lua can return data rather than gaining mutable access to Session or AreaState.

## Rust + Lua runtime implications

Sunbird Ruby remains the research/prototype line.

A separate Rust + Lua runtime can be forked from a selected frozen Sunbird milestone and treated as a stable/shippable runtime rather than replacing Ruby.

The desirable boundary is:

```text
Lua
  gameplay/content decisions
        |
        v
intent/effects
        |
        v
Rust authority
├── persistent Session/ActorState
└── local AreaState
```

Lua should not receive unrestricted mutable engine state.

Cross-implementation fixtures can compare Ruby and Rust semantics without requiring identical internal structure.

## Renderer independence

The v0.4 designation is architectural, not graphical.

Kitty can remain the active renderer throughout the state-model redesign.

Raylib can be experimented with independently in Ruby Sunbird, the Rust + Lua runtime, or both.

Changing state ownership and changing the renderer at the same time is unnecessary.

## Non-goals for the first v0.4 pass

Do not automatically add inventory, equipment, skill trees, quests, save files, an overworld implementation, Raylib, Lua, generic ECS frameworks, or a universal event bus.

The first v0.4 pass should primarily clarify names, lifetimes, persistent actor ownership, runtime bindings, and mutation authority.

## Suggested migration order

1. Freeze/tag v0.3d as the reference milestone.
2. Rename `World` to the selected local-state term, currently `AreaState`.
3. Introduce persistent `ActorState` and move genuinely persistent player combat attributes into it.
4. Make stable-actor ↔ runtime-instance binding explicit.
5. Revisit Session structure so persistent domains do not become parallel loose hashes.
6. Introduce the smallest useful cross-domain effect/resolution boundary.
7. Update BattleMode to consume that boundary instead of mutating Session and local state separately.
8. Re-evaluate terminology and only then add new gameplay systems.

## Open questions

These should be answered by implementation experiments rather than decided abstractly:

- Is `AreaState` the best replacement for `World`?
- Should ActorState live directly under Session or under a dedicated registry object?
- Should `Vitals` remain a nested value object?
- Does attack belong in persistent ActorState for every actor, or only for persistent actors?
- Should local Commands and persistent Effects remain separate?
- Where should local persistent-world changes (opened chest, defeated boss, changed switch) live?
- How should level transitions construct and bind the active party representation?
- Which semantic fixtures should be frozen for the later Rust implementation?

## Core principle

The v0.4 redesign should preserve this distinction:

> Persistent identity and persistent actor state belong above the loaded area. Spatial/local runtime representation belongs to the instantiated area.

Everything else—names, exact objects, and effect APIs—remains open to experimentation.
